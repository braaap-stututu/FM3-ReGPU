## Testing workflow (agreed with the user)
- **The user starts the game with `play.cmd`** (project root: `build\rel\fm3.exe`, debug server on, intro movie skipped since session 18 (`FM3_SKIP_INTRO=0` to see it), saves in `out\user`, profile `Baseline` = a copy of hl360's Baseline save since session 11 (the old `Player` save is damaged, issue H), log `out\run\fm3.log`) and drives to the place a test needs, then reports. Don't repeat launch instructions unless `play.cmd` changes; say when it does, and remove temporary test lines afterwards. Don't script the boot → race route yourself.
- **Since session 12 the user may start with `launcher.cmd` instead** (same game folder and `out\user`; the game still runs in `out\run`, debug server on by default). The launcher writes `out\user\settings.ini` (profile, resolution, MSAA, ...), which `play.cmd` runs read too (only `play.cmd`'s `FM3_PROFILE=Baseline` overrides the profile), so **check the log's `gpu: ReGPU at WxH, msaa N` line** before comparing runs. Each launch copies the previous `fm3.log` to `fm3.prev.log`. Rebuild the launcher with `dotnet build launcher\FM3Launcher -c Release` (`C:\Program Files\dotnet\dotnet.exe` if `dotnet` isn't on PATH); it must be closed to rebuild.
- The game shows a **timer** in the top-left (the log clock, `[time]`, to 0.1 s; `FM3_NO_TIMER=1` hides it): the user's screenshots carry it, so read the log at that time.
- Attach with **`tools/fm3ctl.ps1`** (dot-source it): `Fm3 "status"`, `Fm3 "capture"` (draw list into the log, resolved images to `out\run\out\res`, textures to `out\run\out\capture\tex`), `Fm3 "ps <hash> tint 1,0,1"` / `"ps <hash> <hlsl expr>"` / `"ps <hash>"` (restore), `Fm3 "hlsl <hash> out/hlsl/x.hlsl"` (**no spaces in that path**), `Fm3 "switch REGPU_X 1"`, `Fm3 "peek A6375000 4096"` (physical memory via the `A0000000` mirror; guest heap addresses work too, max 4096 bytes), `Fm3 "find TEXT"` (guest addresses holding a string: session 15 found the in-memory game database `gamedb.slt` this way; decode a 1 KB page with `tools/analysis/sqlpage.py`), `Fm3 "shots N dir raw"` (N consecutive 640x360 RGBA frames: flicker work, session 16), `Fm3 "env REGPU_FREEZE_RESOLVES <hex>,..."` (those images keep their content: which resolve carries a flicker), `Fm3 "env NAME value"` (set an env var live, e.g. `FM3_WRITEBACK=WxH,...` to write resolves of those sizes back to memory), `switch REGPU_TRACE_RESOLVES 1` (log every resolve), `Save-Fm3Shot name.png` (to `out\shots`). You may pause the game yourself (`press START`).
- **Restarting the game yourself (allowed by the user, session 19):** for boot/menu checks and between test runs, close it with `Get-Process fm3 | % { $_.CloseMainWindow() }` (it saves on exit as normal), then start `play.cmd` hidden from PowerShell (`Start-Process cmd.exe '/c "<root>\play.cmd"'`). Env vars set in that PowerShell call reach the game (e.g. `$env:FM3_PERF_PRESET`). The virtual pad is unreliable on the title screen (`hold A` 300-600 ms, or `press START`, sometimes twice). The user still drives to races. Option bytes in memory: `Fm3 "peek/poke <addr> <hex>"` (options object `0x82C21C60` + offset from `xref.py options`; many are only read at load, so a live poke may do nothing).
- **Rebuild needs the game closed**: ask the user to close it, then `tools\vcenv.cmd ninja -C build/rel fm3`. After any change to ReGPU's HLSL preamble, boot and grep the log for `failed to compile` first.
- Method that found every session-8 bug: pause → live `switch` A/B → `capture` → tint candidates to find the draw → `hlsl` → show single terms with `ps` edits → **measure numerically** (`tools/analysis/`: `pngstat.py` brightness/edge metrics, `boxes.py` two-box mean/detail, `crop.py` crop+enlarge, `bandmap.py` block detail map, `strips.py` decode memory dumped via `peek`, `compose_pc.ps1` a draw's constants; box coordinates are hard-coded, edit per scene) instead of judging by eye → compare with hl360 when unsure what "correct" looks like. Read ReGPU's `CLAUDE.md` (in the submodule) for its rules: game-neutral fixes go in ReGPU behind a `REGPU_*` switch; game-specific ones go in `src/gpu_host.cpp` hooks.
- **Sun flare tests:** no race start grid shows the flare; ask the user to drive to a sun-facing spot (the "Montserrat sun spot") and pause there. Grids are fine for fps A/B.
- **Live shader edits:** `ps` expressions name registers `r2`, not `r[2]`; a compile error silently skips the draw, so grep the log for `failed to compile` and wait until the edit reports ready (a few seconds) before screenshotting. `vs <hash> <statement>` runs at the shader's end over `o[]`, `vc[]`: e.g. tint draws by their own transform (`o[1].xyz = ...vc[12]...`) to tell apart draws that share a shader (session 12).
- **Above 1× resolution** the host picks finer mip levels than the console; the game can rely on its 720p size (session 12: one texture with two different pictures as mips 0 and 1). Suspect this when a bug shows only at higher resolutions.
- **Performance A/B (sessions 13–14):** the debug server's `Fm3 "status"` returns `fps` and `draws` without the perf log: average 6–7 samples. **The perf log (`REGPU_PERF`, launcher `perf_log=1`) costs ~14% fps** by itself, so compare with it off. To measure the CPU side, lower the GPU load in `out/user/settings.ini` (e.g. 1280x720, `msaa=1`; back up and restore the user's file; the game never writes it, the launcher does) instead of raising the cap above 360. Profile a guest thread with temporary `play.cmd` lines `FM3_SAMPLE_THREAD=<id>` (+ `FM3_SAMPLE_CALLERS=1`): t9 = ReGPU's command processor, t7 = the game's render thread (its D3D ring-space wait `sub_824B5048` → `sub_824AAA68` = waiting for the CP); ReGPU's draw thread and workers are host threads the sampler can't follow. Live traces: `switch REGPU_TRACE_SEGMENTS 1` (segment sizes per frame), `REGPU_TRACE_PIECES` (piece times), `REGPU_TRACE_ZPD_RESULTS` (query answers). Start-time ReGPU reads: `REGPU_DRAW_THREAD`, `REGPU_DRAW_THREAD_SERIAL`, `REGPU_DRAW_WORKERS`. Pause on a race's start grid (constant draws) and compare 5–7 s averages of the perf log's `perf: N fps` lines; the perf log needs `REGPU_PERF` (launcher `perf_log=1`, or a temporary `set` line in `play.cmd`). The debug server's `switch` reaches only `REGPU_*`/`PGR4_*` names; our `FM3_*` LiveSwitches follow their env var since session 18, so flip them live with `Fm3 "env FM3_NAME 1"` (`0` or empty = off; logged as `switch: ... (environment)`). Some ReGPU switches are also read once at start (`REGPU_EARLY_FENCES` in `gpu.cpp`, `REGPU_DRAW_WORKERS`, `REGPU_SUBMIT_DRAWS`, `REGPU_LEAN_FETCH`): set those at launch, or the live A/B is not real. ReGPU globals read at static init (e.g. `REGPU_NO_FENCE_ORDER`) must be set with `regpu::driver::SetSwitch`, not the environment. Blocked time (WaitOnAddress/condition variables) is invisible to the sampler (`FM3_SAMPLE_THREAD`).
- **ReGPU patches** live in `patches/regpu-*.patch` (applied/verified by `tools/setup.ps1`). After changing ReGPU, regenerate the patch for your change only and run `tools\setup.ps1 -NoBuild` to verify the stack. Scratch-index method (bash, in `thirdparty/ReGPU`): `export GIT_INDEX_FILE=../../out/scratch.index; git read-tree HEAD`, then `git apply --cached ../../patches/<p>.patch` for every patch in `setup.ps1`'s `$regpuPatches` order (list them with `grep -oE "^\s+'regpu-[a-z0-9-]+'" ../../tools/setup.ps1`; a sed range stops early at a `)` inside a comment), `git diff > ../../patches/<new>.patch`, `unset GIT_INDEX_FILE`; then add the name to `$regpuPatches` and a row to `patches/README.md`.

## Gotchas learned the hard way
- **Line endings:** the global git `core.autocrlf=true` turns patch files into CRLF, so `git apply` fails. Use `.gitattributes` with `*.patch -text` (keep `.cmd/.bat/.ps1` CRLF). hl360 + its SDK already have repo-local fixes. The reference clones' working trees are CRLF too: take patch files from their git objects (`git show HEAD:path`), not by copying.
- **Long paths:** some submodules (vulkan-loader) need `core.longpaths=true` (set repo-locally).
- **Guest addresses move between runs**: diff dumps by content hash / (size, format, first-use order), never by address.
- **Timed key presses drift**: Return both skips cutscenes and toggles pause. Drive the game state-aware (`Test-Paused` checks the RESUME-bar shape twice, then re-confirms).
- **CLI cvars outrank toml** in the ReXGlue SDK (`--profile_xuid=…` overrides `fm3.user.toml`). The route uses profile `E0000BA5E11E0002` and deletes only that save; your `Baseline` save `E0000BA5E11E0001` must be left alone.
- **Don't execute third-party repo code** (e.g. `forza3-recomp/tools/*.py`): the permission classifier blocks it. Read it for ideas, write our own.
- **Windows PowerShell 5.1 `>` writes UTF-16**, which the Python tools can't read: redirect native commands through `cmd /c "... > file"` (as `tools/recomp.ps1` does).
- When writing files through shell heredocs/inline Python, Windows backslashes can turn into tabs/CRs (`\t`, `\r`, `\f`). Use forward slashes or the Edit tool, then check with `grep -c $'[\x01-\x08\x09\x0b\x0c\x0e-\x1f]'`.
- Never link FM2/FM4 `sub_XXXXXXXX` addresses into FM3. Every hook must be re-addressed for this xex.
- **Capture folders keep old files.** `out/run/out/capture/tex` keeps the *first* capture of each address forever, and `out/run/out/res` keeps files from earlier runs: check the file time against this run before reading one (session 9: a "car texture" that was last run's, a "livery" that was the track's sky panorama). Guest addresses move between runs too.
- **A live `ps` edit of an alpha-tested shader:** read the shader's alpha function first (`alpha ref ... (pinfo.x N)`: 2 = equal). Forcing `float4(1,1,1,1)` into an "alpha == 0 passes" shader blocks everything instead of passing it.
- **A captured (traced) frame is not a normal frame.** `Fm3 "capture"` runs that frame slowly with full logging, without the per-frame texture cache and draw workers. A bug can vanish in exactly the frame you capture (session 10: vinyl edits made in traced frames came out right). Compare several captures, and confirm against normal-frame screenshots.
- **Read the whole capture entry for a draw before concluding.** It has `rect corners` for rect lists and (patch `regpu-capture-vertex-floats`) `vf<N> floats:` with the full small vertex buffers. Session 9 blamed the wrong pass twice (a window hole read as a cut, then a "256-row loss" that was frame-to-frame variation).
- **Driving the game for A/B tests:** the debug server's virtual pad (`Fm3 "stick L 0.5 0 200"`, `press`, `hold`) can nudge things in menus/editors, so a live switch sweep runs without the user. Measure the effect with a small script on `Save-Fm3Shot` images.
- **Don't trust "looks fixed" by eye.** In session 8 a change that only darkened the road looked like a streak fix, and a texture I called "uniform" was banded. Measure (box detail/mean) and get the user's confirmation in game.
- **Building FM4's vendored ReGPU from `reference/` is blocked** by the permission classifier (third-party code). CMake still has `FM3_REGPU_DIR`/`FM3_REGPU_FM4` for such A/B builds if the user allows it.
- PowerShell sessions spawned from Bash hit the execution policy; run `.ps1` scripts from the PowerShell tool.
- FM3 draws its 720p 2×MSAA scene in **two EDRAM tiles** (rows 0–511, 512–719). Many ReGPU bugs show up at that seam or in passes that run once per tile (resolves, occlusion queries).
- `reference/` and `dumps/` hold third-party code and game-derived data: keep them out of any repository we create.
- **Swap or restore a save only while the game (ours or hl360) is closed:** FM3 saves on exit and overwrites it (session 11, twice). Check `tasklist` for `fm3.exe` (both builds share the name; `Get-Process fm3` shows the path) and `diff -rq` against the backup afterwards.
- **An A/B run is only clean if nothing else changed** since the run it's compared with (session 11: "write-backs off" runs also carried an unrelated fix and pointed at the wrong cause).
- The **FM4 port's GitHub history** (`Aiden-Piercee/Fuzzy-Rittersport-4-ReGPU`, `gh api repos/.../commits`) has the reasoning behind its ReGPU changes; the local clone is one squashed commit.
