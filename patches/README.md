# XenonRecomp patches

Applied in this order to `thirdparty/XenonRecomp` at `ddd128bcca99fe8bfbb99bea583c972351fa6ace`
by `tools/setup.ps1` (which checks the whole stack against the working tree, so it is safe to re-run).

| # | Patch | From | What |
|---|---|---|---|
| 1 | `xenonrecomp-fm2.patch` | FM2-ReGPU / FM4-ReGPU | PowerPC divides never trap (zero divisor / overflow give a value); MSR[EE] toggles become `PPC_MSR_CHANGED` (the runtime's interrupt lock) |
| 2 | `xenonrecomp-modules.patch` | FM4-ReGPU | Optional function-name prefix per image (several images in one program); warns when unnamed imports become no-op thunks |

`default.xex` on Disc 1), so patch 2's prefix stays unused for now.

## ReGPU patches (ours)

Applied to `thirdparty/ReGPU` at `57143cb79e8dd4de7b776c70867313cd0b1862f2` by `tools/setup.ps1`. Game-neutral
Xenos behaviour, each behind a `REGPU_*` switch, as ReGPU's own rules ask; candidates to send upstream.

| Patch | What | Switch |

| `regpu-fixed16-fetch.patch` | A resolved 16-bit fixed image (copy destination `k_16`, `k_16_16`, `k_16_16_16_16`) read with a **different number format than it was copied in**: back to the 16 bits the console stores (fraction copies hold fraction × 65535, or × 32767 signed; integer copies the integer), then read as the fetch asks (unsigned fraction = bits / 65535, signed fraction = value / 32767, integer = bits). The same format on both sides is unchanged; the border colour is never converted. ReGPU returned the stored values as they were. In FM3 this affects the variance shadow map (resolved as signed integers with exp bias +10, read by its blur as unsigned fractions). History: the first version also converted same-format reads and the border, which darkened the sunlit road and drew a square around the car; corrected (session 8c). It did **not** fix the road streaks (that is the strip write-back in `src/gpu_host.cpp`). | `REGPU_NO_FIXED16_FETCH=1` (start-up) |
| `regpu-zpd-tile-spans.patch` | Occlusion queries under predicated tiling: D3D replays each tile's commands, so a query's ZPD events come as a count-on/count-off pair per tile, and only the last carries the end markers. A second start while counting now pauses the query and the next one resumes it (a new D3D query part); the end sums the parts. ReGPU had counted one span from the first start to the end, including every draw of the next tile's replay. FM3's sun query went from 6,472,508 samples to 5,780: the glare no longer whites out, and the coverage re-draws of the second tile are gone. Also: `REGPU_TRACE_ZPD` logs `RB_SAMPLE_COUNT_CTL` and allows 12 more lines each time it is switched on. | `REGPU_NO_ZPD_SPANS=1` (live) |
| `regpu-resolve-into-image.patch` | A resolve with `rect.top > 0` whose destination address **already holds a resolved image of the same width covering the rectangle's rows** is placed into that image at its own rows. ReGPU treated every full-width resolve with a row offset as a predicated-tiling tile, whose destination is the tile's own row, and subtracted the offset. A real tile names an address where no image starts (FM3's scene tile 2: `18216000`, 512 rows in), so tiles are unchanged. FM3 rebuilds its 512×512 road detail image half at a time, rows 256–511 to the image's own base; as a "tile" that went to a phantom 512×768 image 256 rows earlier, the road image kept a stale blurred lower half, and the asphalt showed smooth bands once the chase camera turned (that's when the half-rebuilds start). | `REGPU_NO_RESOLVE_INTO_IMAGE=1` (live) |
| `regpu-timer-overlay.patch` | Test aid, not Xenos behaviour: a panel in the top-left corner of the picture with the log clock (`LogSeconds()`, the `[time]` at the start of each log line) to a tenth of a second, white on black. The presenter copies it onto the back buffer after the game's frame (like the shader-compile panel, which moves below it), so it is in window screenshots but never in the guest's images. Also shown while the shader-compile hold repeats the last frame. Adds `double LogSeconds()` to `log.h`; a port with its own log must provide it. Off unless set; FM3's `src/gpu_host.cpp` sets it (`FM3_NO_TIMER=1` hides it). | `REGPU_TIMER=1` (live) |
| `regpu-cube-2101010.patch` | **k_2_10_10_10 textures** (Xenos format 7: X in bits 0–9, Y 10–19, Z 20–29, W 30–31) are decoded (8 bits kept per channel; the fetch's exponent adjust is applied in the shader as for any format). They were unsupported and decoded to nothing: FM3's showroom/garage reflection cube is this format (256×256, mipped, read from memory), so it was black: chrome black, paint without reflections. Also, cube maps read from memory: each face's level 0 is now staged at its own place in the upload ring and copied from there; before, it was written at `offset + faceBytes·i` but copied from the running offset, so one-level cubes showed face 0 on every face and mipped cubes got other levels' bytes in level 0. | `REGPU_NO_2_10_10_10=1` (live, textures decoded after), `REGPU_NO_CUBE_FACE_STAGING=1` (live, part of the cube's hash) |
| `regpu-resolve-into-enclosing.patch` | A colour resolve whose destination lies **inside an image resolved earlier** (same pitch, format and bytes per pixel; a whole number of 32×32 tiles past its base, i.e. texel (x, y) of the tiled image; the declared height exactly the rows left below y) is also drawn into that image at (x, y), as the copy writes it on the console. The outermost such image wins (the parts' own images match too). The pass's host scale and the image's may differ, so the blit shaders gained a source step and origin (two more root constants; defaults reproduce the old reads). FM3 builds a car's 2048×2048 texture (body, parts, vinyls) this way: four 2048×512 strips and, per vinyl edit, one rectangle per changed region; each became an image of its own, and the car read the one at the base: vinyls invisible. Each copy is still also resolved as its own image. | `REGPU_NO_RESOLVE_INTO_ENCLOSING=1` (live) |
| `regpu-enclosing-writeback.patch` | A resolve drawn into an enclosing image (previous patch) whose image is **written back to memory** (by the port's `resolveWriteback` hook, Now or Deferred) also writes its rectangle of that image back, Deferred (in memory before the next fence, no stall). On the console the copy lands in memory inside the image anyway; ReGPU wrote only the base resolve, so a title that reads the finished image on the CPU found the base without the parts. FM3 builds each car's livery (2048×2048 and 1024×1024) from strips and vinyl regions and compresses it to DXT on the CPU: written back without the parts, the car had no vinyls or badges in races (issue B2). | `REGPU_NO_ENCLOSING_WRITEBACK=1` (live) |
| `regpu-enclosing-big-pass.patch` | Two gaps in `ResolveIntoEnclosing` for passes drawn in tiles: (1) a **big pass's image is kept at the pass width** (the resolve clamps it to `BigPassSize()`, pitch × 64/65 of the surface: a 1400-wide 4× surface copied with pitch 1408 makes a 1378-wide image), so its later tiles, which name the copy pitch, never matched it; the image now matches either width. (2) A **last tile whose rectangle is rounded up to 8 rows past the image** (88 rows copied, 86 declared) was refused; it is clipped to the image (the draw already was). FM3 renders each big vinyl region's side view as a 4×MSAA pass in 224-row tiles: only the first tile reached the image, so the vinyls on the car's sides and hood stopped at a straight line (issue B). | `REGPU_NO_ENCLOSING_PASS_WIDTH=1`, `REGPU_NO_ENCLOSING_ROW_CLIP=1` (live; take effect at the next build of the pass, e.g. a car load) |
| `regpu-writeback-safety.patch` | Three fixes after a car vanished from the garage (FM3 issue H, session 11). (1) The big-pass width match of `regpu-enclosing-big-pass` applies **only when the current pass is a big pass**: for an ordinary pass the clamp is the 1280-wide output, and a 704×264 copy with pitch 2048 (a car's bumper region) matched any 1280-wide image below it (a menu poster showed the bumper's vinyl). (2) A deferred write-back **skips memory the title has written since the resolve** (dense hash of the bytes it covers, taken when queued and again before writing; our own write-backs to the same image don't count), as the FM4 port's ReGPU does: the console writes a resolve when the GPU runs it, ours lands before the next fence or a frame or two later. Logged as `writeback: … the memory changed since the resolve`. (3) The **written-back mark is cleared** when a resolve at the same address isn't written back: it used to stay with the address after the title reused it, so a later resolve drawn into that image (e.g. through the bug in (1)) was written into memory that held other data. Together (1) and (3) are the likely cause of the vanishing cars: with them the car survived the same sequence that lost it, without (2) firing. | `REGPU_NO_ENCLOSING_PASS_WIDTH=1` (as part of the big-pass match), `REGPU_NO_WRITEBACK_REUSE_CHECK=1`, `REGPU_KEEP_WRITEBACK_MARK=1` (live) |
| `regpu-guest-lod-short-mips.patch` | Textures with a short mip chain (smallest level still 64 texels or more) are sampled at the mip level the console would pick: LOD bias + log2 of the draw scale when rendering above 1x. Such chains can hold separate images per level (FM3 keeps a car's 512x256 picture at level 0 and its 256x128 side-view thumbnail at level 1), and the host's finer pick blended both (FM3 My Cars thumbnails at 1440p, session 12). Full chains keep the sharper host pick. `REGPU_NO_GUEST_LOD_SHORT_MIPS=1` (live) turns it off. |
